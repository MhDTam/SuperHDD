# Direct-volume v5 candidate — 2026-10-19

This update connects a new direct-data-volume driver protocol, a protected
LocalSystem cache owner, desktop controls and fixed-path runtime setup/removal.
The production branch has compiled and passed static analysis. It has not run
on a physical HDD and is not a qualified release.

## Implementation

- `drivers/superhdd-cache-driver/v5/` is a separate candidate. The frozen v4
  driver and its historical binary-bound stress evidence are unchanged.
- The production source policy requires a single, stable ATA/SATA HDD data
  extent, a serial number and positive seek-penalty evidence. Boot/system
  volumes, special-file usage, removable media and ambiguous layouts are refused.
  The backing parent must be a distinct, positively identified ATA/SATA/NVMe SSD
  data volume. A data partition on a system disk remains eligible.
- The cache remains a fully allocated, owned VHDX file with a locked RAW payload
  and source-revalidated persistent records. No physical disk is partitioned or
  formatted. The cache budget, including overhead, cannot exceed 25 decimal GB.
- A separate VM build accepts only the isolated SCSI/SAS test policy; the
  production client and driver reject that mode.
- The LocalSystem owner checkpoints the exact source/cache identities before
  configure. Crash recovery reconciles only its protected owned session.
- The public authenticated pipe exposes status/telemetry. Pause, resume and clear
  use a separate administrators/SYSTEM pipe. Stop disables automatic restart and
  preserves the user's stopped intent across reboot. Start restores recovery.
- Desktop actions use a bounded typed payload and the exact protected Program
  Files helper. Release hashes are checked before requesting Windows elevation.
  Development builds refuse activation before creating setup state.
- Runtime installation, enrollment and removal use fixed paths and exact service
  ownership. Removal preserves unknown files, foreign filters and uncertain
  active storage. The signed runtime installer is separate from the desktop NSIS
  development package.

## Verification

The local result is consolidated in `artifacts/direct-v5-evidence.json` by
`scripts/record-direct-v5-audit.cjs`. It records the exact current source/payload
hashes, Rust tests, browser tests, driver policy tests, static analysis, installer
syntax/native-helper compilation, release refusal and native desktop results.
Mocked browser controls prove UI behavior; they are not kernel-runtime evidence.

The first native v5 VM run used a newly attached SAS parent as its source and a
different virtual parent for the private cache. The actual LocalSystem cycle
passed byte comparison, SSD hits, write invalidation, pause/clear/resume, normal
reopen, automatic process-crash recovery and restricted-user denial. Its probe
removed its owned service/cache fixtures. The wrapper then failed at driver
cleanup because it attempted SCM STOP on a PnP filter (error 1052). That cleanup
path now uses PnP removal and registration deletion. The old run remains a failed
overall run; it is not relabelled as a complete pass.

The cleanup helper now restores the known default v4 volumes before invoking
their shutdown verifier. Launching elevation through the interactive Windows
shell resolved the earlier invisible permission request. A second run passed
the probe but exposed SCM's delayed deletion of a loaded PnP registration. The
wrapper now checks registration/filter absence after a cold boot.

The earlier complete run `cdca6b7264934a2d94576394085aa645` used the current
service/probe/driver hashes. All 13 runtime checks passed. Its owned parent files
were removed; cold-boot inspection confirmed no v5 driver registration/filter,
owner service or private state. The final guest state is Off with zero assigned
memory and no active host cache driver. This is cleanup-after-boot proof, not
qualification of an active physical cache across power loss or cold boot.

The subsequent [current-machine check](2026-10-19-current-machine.md) defers
publication and uses only new disposable files on the existing disks. Its v5
run `957541032f134f52b3c12f5d31993278` places the guest source VHDX on the real
D: HDD and the cache parent on M: SSD. The current source-bound service cycle,
cleanup after reboot and final shutdown pass. This is a guest-driver test with
host HDD/SSD backing, not a physical-source driver installed on the host.

## Remaining release requirements

1. Extend direct-v5 testing to sustained load, low-memory, power and PnP
   qualification. The current complete VM lifecycle/cleanup run is a scoped proof.
2. Qualify the production branch on disposable physical HDD/SSD data volumes on
   Windows 10 and Windows 11, including cold boot, power interruption, rollback
   and uninstall while active. VM SAS results do not establish these properties.
3. Obtain a Microsoft-accepted kernel signature for that exact qualified driver.
   The user requires a free solution and has no publisher account or EV
   certificate. No confirmed free publisher sponsor is available.
4. Run the signed runtime setup/control/remove path and its failure matrix on
   the qualified machines. The current installer checks are source/build checks.

`scripts/package-qualified-runtime.ps1` refuses an unsigned image, incomplete
hardware evidence or a service built for a different driver hash. A qualified
service embeds `SUPERHDD_QUALIFIED_DRIVER_SHA256`; the desktop additionally embeds
the resulting helper hash. Neither variable is set for this development build.
No test driver or test-signing policy has been installed on the host.
